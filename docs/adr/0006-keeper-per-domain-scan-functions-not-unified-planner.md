# Keeper stays per-domain scan functions, not a unified action planner

The keeper's decision kernel is a set of pure functions over a `KeeperWorld` snapshot — `scanLiquidationCandidates`, `scanStaleIndexMarkets`, `scanTriggeredOrders`, and `findAdlAction` — each returning the work to do for one domain as plain data, with the dedup/serialize/submit mechanics left to the hot and cold loops. The architecturally cleaner-looking alternative was a single `planKeeperActions(world, config)` returning a `KeeperAction[]` tagged union, with the loop reduced to a generic plan-executor.

We rejected the unified planner because it collapses a distinction the cadence design depends on. The hot loop runs liquidations only, on a sub-second adaptive cadence, because liquidation latency is the keeper's tightest requirement; the cold loop runs index updates, TP/SL execution, and ADL on a fixed 5s cadence. A single action list would immediately have to be re-partitioned by cadence inside the planner, reintroducing the split it was meant to remove. The per-domain functions also match the shape of the kernel that already exists and is tested (`scanner.test.ts` drives `scanLiquidationCandidates`/`findAdlTarget` off hand-built `KeeperWorld` snapshots), so each newly extracted predicate becomes testable exactly like the two that already were — versus inventing a new action-union surface to assert against. One planner is a hypothetical seam: nothing today consumes the full action list as a unit. Revisit when a third cadence tier appears, or when actions need cross-domain prioritization — for example "submit at most N transactions per tick across all action types, ranked by urgency" — at which point a unified plan with a global ranking concentrates scheduling logic that independent per-domain functions cannot express, and the action union pays for itself.
